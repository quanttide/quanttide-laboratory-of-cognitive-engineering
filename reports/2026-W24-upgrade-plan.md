# 多租户技术升级方案

依据：量潮认知工程实验室从 journal 数据迁移验证的 `schema2.yaml`（质量评分 4.14/5）。

---

## 一、升级阶段

**总周期**：3-4 个月交付 + 持续演进。每阶段 ≤3 周，阶段间设缓冲期。

### M0：认知对齐（第 1 周）

**核心任务**：
- 与 CTO/架构负责人完成范式认知对齐——多租户涉及路由、隔离、数据扩散，非加 tenant_id 可解决
- 确定当前隔离模式起点（推荐：逻辑隔离共享 DB）
- 建立决策记录机制（ADR）

**交付物**：对齐结论 + 升级路线图签核

### M1：基础设施（第 2-4 周）

**核心任务**：
- 逻辑隔离层搭建（租户路由 + 数据隔离边界）
- 建立回退机制（每阶段可回滚）
- 第一个 POC 验证

**触发条件**：第三个租户提出同类需求 → 进入下一级隔离

### M2：核心改造（第 5-8 周）

**核心任务**：
- Schema 隔离（如果需要）
- 核心业务模块改造
- 治理机制落地（底线约束 + 决策记录）

### M3：迁移治理（第 9-12 周）

**核心任务**：
- 存量数据迁移
- 治理规则沉淀
- 文档化

### 持续演进

- 隔离复杂度随租户数递增
- 按"第三个同类需求"触发升级
- 每阶段结束时做准入/准出评审

## 三、需验证项（⚠️ 准入期确认）

以下结论依赖客户特定条件，需在 M0 完成验证：

| 条件 | 验证方法 | 不通过则 |
|------|---------|---------|
| 客户 CTO 亲自参与认知对齐 | 确立对接人身份 | 调整对齐方式或拒绝入场 |
| 客户有底线约束机制（验收标准/熔断红线） | 审查现有项目管理流程 | 先帮助建立机制再推进 |
| 顾问能获取客户业务日历和关键节点 | 确认沟通渠道 | 调整交付节奏 |
| 客户接受显式化决策过程 | 访谈确认 | 改用其他追溯方式 |

## 四、报价结构（基于关键参数）

```
M0 认知对齐    → 固定价：¥XX（1 周）——含创始人访谈 + 条件验证
M1 基础设施    → 固定价：¥XX（3 周）——含逻辑隔离 + POC
M2 核心改造    → 按实际范围报价（预估 3-4 周）
M3 迁移治理    → 按数据量报价（预估 2-3 周）
```

> 实际报价需结合客户的具体系统规模和团队人数。以上为框架结构。

## 五、下周一开始做什么

如果客户签了，M0 第 1 天的工作清单：

1. **第 1-2 天**：完成准入诊断（验证条件清单 + 创始人 30 分钟访谈）
2. **第 2-3 天**：确认 CTO 是否亲自参与对齐——验证 causal#6（需验证）
3. **第 3-4 天**：审查客户项目管理流程——验证 causal#8（需验证）
4. **第 5 天**：产出对齐结论 + 签署升级路线图

**第一周结束时，客户应该能回答两个问题：**
- 我从哪里开始？
- 我付的钱买到了什么？
