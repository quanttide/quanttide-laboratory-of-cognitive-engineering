# PoC 文档质量评估

评估对象：`reports/2026-W24-poc.md`
评估框架：`docs/customer-checklist.md`（5 问）

## 逐问评估

### Q1：可信吗？

**客户问**：凭什么信你说的？数据来源是什么？

| 有什么 | 缺什么 |
|--------|--------|
| 明确引用升级方案 M1 阶段 | 没说明"候选模块选型排序"的依据是什么——为什么用户权限是 1、核心单据是 3？ |
| 架构图清晰（当前→目标） | 没有说明 tenant_id 注入的可靠性保障（万一漏注入一条查询，数据就泄露了） |
| 验证条件量化（P-1 到 P-4） | |

**评分**：⭐⭐⭐⭐
**修复**：补充选型排序的量化依据（如耦合度分析数量），补充 tenant_id 注入的审计机制。

### Q2：跟我有关吗？

**客户问**：说的是我的系统吗？还是通用模板？

| 有什么 | 缺什么 |
|--------|--------|
| "存量单租户功能改造为逻辑隔离"——场景清晰 | 没有客户系统名称，没有说"针对你的 XX 系统" |
| 三个候选模块（权限/单据/配置）——具体 | |

**评分**：⭐⭐⭐⭐
**修复**：在开头加一行"本 PoC 方案针对的是你的 XX 系统，具体以你方确认的候选模块为准。"

### Q3：风险在哪？

**客户问**：哪些是确定的？哪些还要再看看？

| 有什么 | 缺什么 |
|--------|--------|
| ✅ P-1 到 P-4 通过条件明确 | ⚠️ F-3（代码文件超过 20 个）是中止条件——但为什么是 20 个？阈值依据？ |
| ✅ F-1 到 F-3 不通过条件明确 | ❓ 没写"如果 PoC 通了但性能下降 10%，能不能接受"——只有 pass/fail，没有 borderline |
| ✅ 决策树（通过/未通过/触发） | |

**评分**：⭐⭐⭐
**修复**：补充 F-3 阈值的依据（基于架构师评估），新增 borderline 处理策略（pass/fail 之间的灰色地带）。

### Q4：能直接用吗？

**客户问**：看完我能给我团队发指令吗？

| 有什么 | 缺什么 |
|--------|--------|
| ✅ "当前→目标" 架构转换明确 | ❌ 没有代码级示例——"tenant_id 注入"听起来抽象，一个代码 diff 示例就能消除歧义 |
| ✅ 角色+投入+工期表完整 | ❌ 没有环境要求——"在哪台机器上做？用什么数据库？" |
| ✅ 产出物 3 项具体 | |

**评分**：⭐⭐⭐
**修复**：加一个 DAO 层改造的代码 diff 示例，加环境要求清单。

### Q5：值吗？

**客户问**：比我自己做或找别人做，多给了什么？

| 有什么 | 缺什么 |
|--------|--------|
| PoC 的决策树——比"先试了再说"多了一个退出机制 | 没有说"如果不做 PoC 直接上，风险有多大"——需要对比路径 |
| 验证条件量化——比"试一下看看"多了一组客观标准 | |

**评分**：⭐⭐⭐⭐
**修复**：加一个"不做 PoC 直接升级的对比风险表"。

## 综合评分

| 标准 | 评分 |
|------|------|
| 可信吗？ | ⭐⭐⭐⭐ |
| 跟我有关吗？ | ⭐⭐⭐⭐ |
| 风险在哪？ | ⭐⭐⭐ |
| 能直接用吗？ | ⭐⭐⭐ |
| 值吗？ | ⭐⭐⭐⭐ |
| **总分** | **3.6/5** |

**最大缺口**：风险的可视化（缺 borderline 策略）+ 可执行颗粒度（缺代码示例和环境要求）。

## 修复建议

1. 补充选型排序的量化依据（耦合度分析）
2. 补充 tenant_id 注入的审计保障机制
3. 增加 borderline 处理策略
4. 增加代码 diff 示例
5. 增加"不做 PoC 直接升级"的对比风险表
