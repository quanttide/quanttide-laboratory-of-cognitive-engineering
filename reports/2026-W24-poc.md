# PoC：多租户逻辑隔离验证

基于升级方案 M1 阶段的核心假设验证。

## 验证目标

**在 2 周内，将一个存量单租户功能改造为逻辑隔离的多租户版本，验证范式转换的可行性和成本。**

## 范围

**选型标准**：业务价值高、技术依赖少、改造风险低的三方交叉。

| 候选 | 业务价值 | 技术依赖 | 改造成本 | 排序 |
|------|---------|---------|---------|------|
| 用户权限模块 | 高 | 少 | 低 | 1 |
| 核心业务单据 | 高 | 多 | 高 | 3 |
| 基础配置管理 | 中 | 少 | 低 | 2 |

**推荐选型**：用户权限模块。

## 架构方案

### 当前（单租户）

```
请求 → Controller → Service → DAO → 单库单表
```

### 目标（逻辑隔离）

```
请求 → 租户中间件 → Controller → Service → DAO → 共享库 + tenant_id 过滤
                    ↑
              从请求头/Token 提取 tenant_id
```

**隔离范围**：
- 表级别：user、role、permission 表新增 tenant_id 列
- 路由级别：所有写操作自动注入当前 tenant_id
- 查询级别：所有读操作自动追加 WHERE tenant_id=?

**不改范围**：
- 不拆分数据库实例
- 不分库
- 不修改已有历史数据的读取逻辑（默认 tenant_id = null 为存量数据）

## 验证条件

### 通过条件（全部满足）

| # | 条件 | 测量方式 |
|---|------|---------|
| P-1 | 新增租户后，两个租户的用户完全隔离 | 分别登录两个租户，用户列表无交叉 |
| P-2 | 存量单租户数据不受影响 | 原有查询返回结果与改造前一致 |
| P-3 | 新增租户的创建成本 < 1 人天 | 从配置到上线的操作时间 |
| P-4 | 不改动已有业务代码（仅改 DAO 层） | 代码 diff 统计 |

### 不通过条件（任一触发）

| # | 条件 | 后果 |
|---|------|------|
| F-1 | tenant_id 注入导致已有功能报错 | PoC 失败，需回退 |
| F-2 | 新增 tenant_id 后查询性能下降 > 15% | 需评估索引方案 |
| F-3 | 涉及改动的代码文件超过 20 个 | 改造成本超预期 |

## 资源与排期

| 角色 | 投入 | 工作内容 |
|------|------|---------|
| 开发 | 5 人天 | 租户中间件 + DAO 改造 + 测试 |
| 架构师 | 1 人天 | 代码审查 + 成本评估 |
| 测试 | 1 人天 | P-1 到 P-4 验证 |

**总工期**：10 个工作日（含缓冲）。

## 产出物

1. `tenant-middleware` 模块源码（可复用到后续阶段）
2. PoC 验证报告（P-1 到 P-4 逐条结果 + 性能对比数据）
3. 全量改造成本估算更新（基于 PoC 的实际改造成本给出 M1-M3 的修正估算）

## 决策树

```
PoC 结果 ↓
          ├── 全部通过 → 进入 M1 正式阶段（成本估算已校准）
          ├── P 未通过 → 分析根因，调整架构方案后重跑 PoC
          └── F 触发   → 暂停升级，重新评估多租户方案选型
```
