# PoC：多租户逻辑隔离验证

源自 `data/schema2.yaml`（保留类 6 条 + 需验证类 4 条 + 映射 4 条）。

## 验证目标

### 从 causals 推导

| schema causal | 对 PoC 的约束 |
|-------------|--------------|
| causal#1（保留—技术本质）：未完成范式认知 → 用单租户思维改造 | PoC 不只是验证技术可行性，同时验证团队是否完成了"多租户涉及路由、隔离、数据扩散，非加 tenant_id 可解决"的认知转换 |
| causal#3（保留—工程原则）：第三个租户提出同类需求 → 进入下一级隔离模式 | PoC 不做完整多租户架构。只做逻辑隔离，不做 schema 隔离 |
| causal#4（保留—风险控制）：POC 验证可行 → 全面推广 | 本次 PoC 就是 M0→M1 的关卡。通过才进入正式阶段 |
| causal#5（保留—工程底线）：缺少回退机制 → 升级失败后无法恢复 | PoC 的每次变更必须有回退方案 |

**结论**：PoC 验证两件事——(1) 逻辑隔离的工程可行性，(2) 团队的范式认知成熟度。任一失败则 PoC 不通过。

## 范围

### 选型约束

| schema 来源 | 约束 | 选型结论 |
|-----------|------|---------|
| causal#3（保留—工程原则）：第三个租户提出同类需求触发升级 | PoC 范围应匹配"已有明确的多租户需求"的功能，不做预测性设计 | 选"已有至少两个客户/场景共享需求"的功能 |
| mapping#2（保留）：避免过度设计 → 从逻辑隔离起步 | PoC 不改数据库实例，不改分库策略 | 约束隔离层级为逻辑隔离 |
| mapping#3（保留）：维持团队动力 → 每阶段 ≤3 周 | 从 3 周上限扣掉对齐和缓冲，PoC 工期 ≤10 个工作日 | 2 周 |

### 选型矩阵

基于 causal#3 的"已有明确多租户需求"约束：

| 候选 | 已有需求证据 | 改造成本 | 认知验证价值 |
|------|------------|---------|------------|
| 用户权限模块 | 大部分 SaaS 产品天然面临"不同客户的管理员能看到哪些用户"的问题 | 低（仅在 DAO 层加 tenant_id 过滤） | 高——权限隔离是"多租户不只是加字段"的最直接例证 |
| 基础配置管理 | 不同租户的配置参数不同，但通常每个租户独立配置 | 低 | 中——配置隔离技术难度低，验证不了认知 |
| 核心业务单据 | 部分场景已有不同客户的单据混在一起 | 高（涉及大量业务逻辑） | 高——但改造成本超标，违反 mapping#3 的工期约束 |

**推论**：用户权限模块是唯一同时满足 causal#3（已有需求证据）、mapping#2（不改架构）、mapping#3（2 周工期）的候选。其他候选分别违反至少一条约束。

## 验证条件

### 从 causals 和 mappings 推导

| 条件 | 来源 | 测量方式 |
|------|------|---------|
| P-1 范式认知验证 | causal#1 + causal#6（需验证—信任前提） | PoC 完成后，团队能用自己语言解释"为什么多租户不是加个 tenant_id"，而不只是"我照着文档做了" |
| P-2 隔离有效 | mapping#2（逻辑隔离起步） | 分别登录两个租户，用户列表无交叉。可回退到改造前状态（causal#5） |
| P-3 存量不受影响 | causal#5（保留—工程底线） | 原有查询返回结果与改造前一致，且未修改已有历史数据 |
| P-4 改造成本可控 | causal#3（第三个租户触发）+ mapping#3（≤3 周） | 从骨干开发接手到 PoC 完成 ≤10 个工作日。涉及改动的代码文件在架构师评估范围内 |

### 中止条件

| 条件 | 来源 | 后果 |
|------|------|------|
| F-1 认知验证失败 | causal#1（范式认知缺失→错误改造）+ bias#1（"加个tenant_id就够了"） | PoC 失败。先补认知对齐工作坊（mapping#1），再重跑 |
| F-2 隔离导致已有功能报错 | causal#5（缺少回退→无法恢复） | 立即回退。PoC 失败，需调整方案 |
| F-3 团队在 PoC 中回到单租户思维 | bias#1 + causal#1 | 说明范式认知未完成，PoC 终止（bias#1 已验证为真） |

## 前置条件（需验证类）

| 条件 | 来源 schema | 验证方法 | 不满足则 |
|------|------------|---------|---------|
| CTO 是否亲自参与认知对齐 | causal#6（需验证—伪共识→服从性表演） | 创始人 30 分钟访谈，确认 CTO 的参与意愿 | 调整对齐方式，或拒绝入场 |
| 是否存在底线约束机制 | causal#8（需验证—无底线约束→无尽扯皮） | 审查团队现有开发流程（PR 规范、验收标准） | 先帮助建立机制再推进 |

## 架构方案

由 mapping#2（逻辑隔离起步）和 causal#3（不做 schema 隔离）直接限定：

```
当前（单租户）：
  请求 → Controller → Service → DAO → 单库单表

目标（逻辑隔离，不做 schema/实例隔离）：
  请求 → 租户中间件(注入 tenant_id) → Service → DAO → 共享库 + tenant_id 过滤
                                                                  ↑
                                                            causal#3：不做 schema/实例隔离
```

**不改范围**（由 schema 约束直接限定）：
- 不拆分数据库实例（mapping#2）
- 不分库（mapping#2）
- 不改已有历史数据（causal#5 回退保障）

## 资源与排期

| 角色 | 投入 | 来源约束 |
|------|------|---------|
| 开发 | ≤5 人天 | mapping#3（≤3 周），减去对齐和缓冲 |
| 架构师 | 1 人天 | causal#8 验证（开发流程审查）+ F-3 阈值设定 |
| 产品 | 1 天 | causal#3 确认（是否真的已有第三个同类需求） |

**总工期 ≤10 个工作日**（mapping#3 约束）。

## 决策树

```
PoC ↓
     ├── P-1~P-4 全部通过 → M1 正式阶段
     ├── P-1 未通过 → 补 mapping#1（认知对齐工作坊）→ 重跑 PoC
     ├── F-2 触发     → 回退（causal#5），调整方案
     └── F-1/F-3 触发 → 范式认知未完成，暂缓升级（bias#1 已验证）
```
