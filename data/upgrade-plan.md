# 技术升级方案

**客户**: SaaS 平台 · 单租户 → 多租户升级  
**源**: 认知工程图式迁移框架（基于 quanttide-founder/2026-W23）  
**日期**: 2026-W24

---

## 范式认知：这不是功能开发，是架构升级

多租户不是"在 User 表加个 tenant_id"。它意味着以下层面的范式转换：

| 当前（单租户思维） | 目标（多租户思维） |
|-------------------|------------------|
| 数据天然属于所有人 | 所有数据按租户隔离 |
| 配置就是改代码 | 配置是租户属性，运行时生效 |
| 出问题修就行 | 租户 SLA 承诺，不能相互影响 |
| 一个版本所有人用 | 不同租户可能在不同版本上 |
| 运维靠人盯 | 运维按租户维度自动化 |

**认知对齐是第一步也是最关键一步** — 如果团队带着单租户思维做多租户，结果就是"加了个 tenant_id 的伪多租户"。

## 现状评估

### POC：一周验证核心瓶颈

在动手改造前，用最小 POC 回答三个问题：

| 问题 | POC 方法 | 判断标准 |
|------|---------|---------|
| 当前代码与数据的耦合程度 | 选取一个核心模块，强行把它的数据按 tenant_id 隔离 | 如果改动涉及 3 层以上代码 → 耦合高 |
| 团队对多租户的理解水平 | 让团队各自写一份多租户方案 | 如果三份方案差异大 → 认知未对齐 |
| 现有基础设施的扩展能力 | 尝试为第二个"租户"准备一套独立资源 | 如果需要手动操作超过 30 分钟 → 自动化不足 |

### 风险矩阵

| 风险 | 概率 | 影响 | 缓解策略 |
|------|------|------|---------|
| 团队用单租户思维改造 | 高 | 高 | M0 认知对齐 + 架构评审 |
| 过度设计隔离机制 | 中 | 中 | 三原则：出现三次才抽象 |
| 数据迁移损坏 | 中 | 高 | 灰度迁移 + 全量回滚 |
| 升级周期过长丧失动力 | 高 | 中 | health 节奏管理：每阶段有产出 |
| 多租户模式选型错误 | 中 | 高 | POC 先行验证，保留切换余地 |

## 升级策略

### 核心策略：同步推进（org 人治→法治模式）

| 策略 | 对应源 schema | 做法 |
|------|-------------|------|
| 从被动到主动 | infra → anti-fragile | 不做"当前能跑就行"，做体系化设计 |
| 制度化与保留弹性 | org → 法治与人治同步 | 建标准但留例外通道 |
| 反脆弱设计 | org → 反脆弱 | 升级过程本身要容错（灰度、回滚） |
| 三次抽象 | infra → 抽象门槛 | 第三个租户再做通用层 |

### 多租户模式选择

| 模式 | 适用场景 | 源映射 |
|------|---------|--------|
| **共享 DB + 逻辑隔离**（tenant_id 行级） | 早期、低成本、快速上线 | innov → POC 先行 |
| **共享 DB + Schema 隔离**（独立 schema） | 数据安全要求适中，管理成本低 | infra → 体系化 |
| **独立 DB 实例** | 高安全要求、SLA 独立 | org → 反脆弱 |

**建议**: 从共享 DB + 逻辑隔离起步（与 POC 范式对齐），预留 Schema 隔离的升级路径。当第三个租户提出安全需求时（infra 三原则），进入 Schema 隔离。

## 实施路径

### M0：认知对齐（1-2 周）

- 团队完成范式认知工作坊（product 范式迁移）
- 跑一个最小多租户 POC（innov），验证核心瓶颈
- 确定多租户模式选型
- 建立架构决策记录机制（ADR = think 辩论→章程）
- **里程碑**: 一份共识的多租户技术方案

### M1：基础设施层（2-3 周）

- 租户路由中间件（infra 主动设计）
- 租户管理服务（创建/配置/启停）
- 自动化隔离策略（按 POC 验证结果选择模式）
- 数据迁移方案 + 回滚预案（org 反脆弱）
- **里程碑**: 可以在隔离环境内创建并运行一个新租户

### M2：核心业务改造（4-6 周）

- 用户/权限模块多租户化（meta 标准化）
- 计费/订单模块多租户化（business 模式验证）
- 存量数据灰度迁移（write 原型→迭代）
- 每两周一次"整合"（回顾、文档、更新规范）
- **里程碑**: 已经上线的老租户 + 新创建的新租户同时稳定运行

### M3：全面迁移与治理沉淀（2-3 周）

- 剩余模块迁移
- 旧系统并行运行 → 下线（org 制度化）
- 治理体系正式建立：租户管理规范、ADR、监控（meta 元智能）
- **里程碑**: 旧系统下线，全量运行在新架构

### M4：持续演进（ongoing）

- 标准化从实践中自然沉淀（meta 标准化后置）
- 自运维/自愈能力建设（meta 系统自我维护）
- 按"三次原则"不断抽象通用能力（infra）

## 节奏管理（health 可持续性）

| 阶段 | 时长 | 交付密度 | 缓冲 |
|------|------|---------|------|
| M0 | 1-2 周 | 低（讨论、验证） | — |
| M1 | 2-3 周 | 高（基础设施开发） | 1 周 |
| M2 | 4-6 周 | 高（核心改造） | 1-2 周 |
| M3 | 2-3 周 | 中（迁移、治理） | 1 周 |
| M4 | 持续 | 低（演进） | — |

**关键规则**: 任何阶段如果连续 3 周无可见产出，就应该停下来重新评估计划（此为 health 的"无意义感对冲"映射）。

## 与通用模板的差异（验证）

对比实验 C 中 LLM 直接生成的方案：

| 维度 | 通用模板（实验 C） | 本方案（图式迁移） |
|------|-----------------|------------------|
| **起点** | 从通用多租户架构出发 | 从创始人认知图式出发，迁移到客户问题 |
| **策略逻辑** | "应做 X" | "因为创始人在 Y 上踩过坑，所以做 X" |
| **节奏** | 每周排期 | 基于 health 的可持续节奏，含无意义感对冲 |
| **模式选择** | 固定三级隔离 | 基于 infra 三原则：第三个租户才做通用层 |
| **团队管理** | 无 | 基于 org 的法治与人治同步、温度保留 |
| **报价逻辑** | 按阶段报价 | 按阶段报价 + 付款节点对齐升级里程碑 |
| **风险处理** | 标准风险清单 | 基于 org 反脆弱的灰度/回滚机制 |

**核心差异**: 通用模板告诉你"做什么"，图式迁移方案告诉你"为什么做这个选择"——每个决策背后都有一个来自创始人实践的因果链。
