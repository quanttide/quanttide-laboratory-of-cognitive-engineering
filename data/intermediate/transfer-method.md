# 图式转移方法草案

从复盘过程中倒推出实际有效的转移程序。

---

## 方法概述

```
源 schema（A 领域） ──→ 映射操作 ──→ 目标结构（B 领域）
                            │
                            ▼
                      记录映射类型 + 决策依据
                            │
                            ▼
                      在 B 领域中组合为新图式
```

**核心原则**: 方法产出的是"如何做映射"的程序，不是"映射出来的具体结果"。

---

## Step 0：确定产出目标

**这是最容易出错的一步。**

| 错误目标 | 正确目标 |
|---------|---------|
| 产出一个针对 B 问题的解决方案 | 产出一个从 A→B 的可复现转移程序 |
| 把问题 B 解决掉 | 记录从 A 到 B 的路径，让下次可以走同一条路 |

**检查**: 如果产出物是"XXX 方案"或"XXX 框架"，就偏了。产出物应该是"转移过程记录"和"转移规则集合"。

---

## Step 1：拆解源 schema

### 1.1 提取核心结构

从每个 domain 的 YAML 中提取：

| 维度 | 含义 | 提取方法 |
|------|------|---------|
| **Entities** | 这个领域的关键概念 | 直接从 schema.entities 取 name 和 attributes |
| **Causals** | 核心因果链 | 从 schema.causals 取 condition → outcome |
| **Boundaries** | 适用范围 | 从 schema.boundaries 取适用/排除条件 |
| **Mappings** | 意图→行动 | 从 schema.mappings 取 intent → action |
| **核心命题** | 一句话总结这个 schema 的"世界观" | 从 biases 的矛盾 + frame 的视角合成 |

### 1.2 标注角色

角色 = 这个 schema 在整体中发挥的功能。从以下维度判断：

- **收敛/发散**：是结构化输出还是探索输出？
- **底座/上层**：是基础条件还是高级应用？
- **主动/被动**：是设计驱动还是响应驱动？
- **元/直接**：是保障其他还是直接产出？

---

## Step 2：做映射

### 2.1 问正确的问题

| ❌ 错误问题 | ✅ 正确问题 |
|-----------|-----------|
| "这个结构在 B 问题上对应什么？" | "这个结构的关系模式，在 B 领域有类似的关系模式吗？" |
| "这个映射到技术升级的什么？" | "这个映射操作本身，可以抽象成什么规则？" |

### 2.2 识别映射类型

| 类型 | 定义 | 判断 | 转移规则 |
|------|------|------|---------|
| **结构同构** | A 的关系结构 ≈ B 的关系结构 | A 的 causals 在 B 语境下有同构的因果链 | 保留 causals 的方向，替换 entities 为 B 的实体 |
| **隐喻迁移** | A 的某个模式在 B 语境中有对应物 | 跨域类比成立（如"POC 范式"从研发迁移到商务） | 验证核心约束在 B 中是否满足；如不满足则为弱隐喻 |
| **反例学习** | biases 中的"信念→事实" | schema.biases 中有清晰的 belief vs fact 对立 | 直接复制——否定性知识（不要做什么）往往跨域适用 |
| **约束标记** | boundaries 中的限定条件 | schema.boundaries 中的"排除"和"需要" | 检查 B 领域是否在约束范围内；不在则标为不可迁移 |

### 2.3 记录决策过程

对每个映射，至少记录：

```
源 schema: [domain name]
映射类型: [同构/隐喻/反例/约束]
源结构: [entities/causals/mappings 中的具体内容]
目标对应: [在 B 领域中的对应物]
推理路径: [从源想到目标的完整推理过程]
保留了什么: [结构中的哪些部分被保留]
丢弃了什么: [哪些部分被丢弃]
```

---

## Step 3：按映射方式分类

不要按"客户问题的解决阶段"分类，要按"映射操作的类型"分类。

```
✅ 正确分类轴:
- 结构同构的映射集合 → 可提炼为"关系保留"规则
- 隐喻迁移的映射集合 → 可提炼为"类比验证"规则
- 反例学习的映射集合 → 直接可复用
- 约束标记的映射集合 → 不可迁移的红线

❌ 错误分类轴:
- 现状评估、升级策略、实施路径...（这是客户问题的解决结构）
```

---

## Step 4：打包为可执行程序

将转换规则写成可执行的步骤清单，格式为：

```
IF 源结构类型 = [causal/entity/mapping/boundary]
AND 映射类型 = [同构/隐喻/反例/约束]
THEN 转移操作 = [保留 X，替换 Y，丢弃 Z]
```

---

## Step 5：验证

用方法重新做一次转移（同一个源 → 同一个目标），检查：

1. 两次的映射结果是否一致？（可复现性）
2. 如果一致，方法是可靠的
3. 如果不一致，哪里出了问题？需要补充什么规则？

---

## 当前已知的映射规则（初始集）

| 源结构类型 | 映射类型 | 转移操作 |
|-----------|---------|---------|
| causal（因果链） | 结构同构 | 保留 cause→effect 方向，替换 entities |
| boundary（排除条件） | 约束标记 | 直接复制为"不可迁移"标记 |
| biases（信念→事实） | 反例学习 | 直接复制为"避免的陷阱" |
| entities（实体+属性） | 隐喻迁移 | 在 B 域找功能对等的实体，验证属性是否匹配 |
| mappings（意图→行动） | 结构同构 | 保留 intent→action 模式，重新填充 B 域内容 |
