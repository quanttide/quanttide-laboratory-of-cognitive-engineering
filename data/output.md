# 新图式：技术升级

从创始人的 9 个源图式迁移到"单租户→多租户技术升级"问题后合成的新图式。

---

## Entities

| 实体 | 属性 |
|------|------|
| 升级阶段 | 认知对齐, 基础设施, 核心改造, 迁移治理, 持续演进 |
| 隔离模式 | 逻辑隔离, Schema 隔离, 实例隔离 |
| 治理机制 | ADR, 租户管理, 自运维 |
| 节奏信号 | 里程碑, 倦怠对冲, 缓冲期 |

## Causals

- 源 product: 范式认知先行 → 团队不自欺（不是加字段，是架构重构）
- 源 health: 持续 3 周无产出 → 动力归零 → 每阶段必须有可见里程碑
- 源 org: 制度化与保留弹性同步 → 标准化与开发者体验不冲突
- 源 infra: 第三个同类需求出现前不做通用抽象 → 隔离模式从简起步
- 源 innov: POC 验证 → 全面推广 → 技术选型先 PoC 后承诺
- 源 meta: 标准化是结果非目标 → 规范从实践中生长，不预设计

## Boundaries

- 适用于：已有认知工程数据的创始人型组织
- 排除：无架构决策权、纯外包团队
- 需要：团队对"这是范式升级非功能开发"达成共识
- 限制：创始人一人+AI 模式迁移到团队时需要适配决策流程（ADR）

## Mappings

| 意图 | 行动 | 源图式 |
|------|------|--------|
| 防止团队用旧思维做新架构 | M0 认知对齐工作坊 + 最小多租户 POC | product → think |
| 不陷入过度设计 | 从最简单的逻辑隔离起步，等第三个租户再抽象 | infra, innov |
| 维持团队动力 | 每阶段≤3 周，阶段间设缓冲期，里程碑可见 | health |
| 不让升级成为新压力源 | 升级节奏与 org 转型节奏对齐，同步推进 | org |
| 架构决策可追溯 | 每项决策记录为 ADR（辩论→章程模式） | think |
| 规范不阻碍实践 | 让规范在升级过程中自然沉淀，非预设计 | meta |

## Properties

| 属性 | 值 |
|------|-----|
| 升级模式 | 渐进迁移，非大爆炸重写 |
| 隔离策略 | 逻辑共享起步 → Schema 隔离就绪 → 实例隔离可选 |
| 总周期 | 3-4 个月（M0-M3）+ 持续演进（M4） |
| 决策密度 | 前期高（范式认知+模式选型），后期低（执行+治理） |

## Dynamics

| 维度 | 趋势 |
|------|------|
| 隔离复杂度 | 随租户数量递增，按三原则触发升级 |
| 治理成熟度 | 随升级过程自然递增，不预设治理阶段 |
| 团队认知 | 从"加字段"到"范式重构"跨越最大，之后递减 |

## Biases

| 信念 | 事实 | 源图式 |
|------|------|--------|
| 加个 tenant_id 就够了 | 需要范式级重构，从数据模型到运维体系 | infra → 体系化 > 堆叠 |
| 一步到位最省事 | 渐进迁移更可控，每阶段可回滚 | org → 反脆弱 |
| 标准先定好再动手 | 标准化在实践中自然形成 | meta → 元智能 |
| 升级是技术问题 | 最大瓶颈是团队认知和节奏管理 | health → 元意图 |
