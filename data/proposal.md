# 技术升级方案

## 从单租户到多租户架构升级

---

## 核心论点

多租户升级不是功能开发，是架构范式升级。成功的升级依赖三件事：**认知对齐先行、渐进迭代推进、节奏管理贯穿始终**。

---

## 升级框架

```
认知对齐 ──→ 基础设施 ──→ 核心改造 ──→ 迁移治理 ──→ 持续演进
（M0）        （M1）        （M2）        （M3）        （M4）
   │             │             │             │
   └────── 团队认知阻力 M0 最大，之后递减 ──────┘
   
           总周期：3-4 个月交付 + 持续演进
```

---

## 现状诊断：你的团队处于哪个状态？

### 三个快速判断

| 问题 | ✅ 健康 | ⚠️ 注意 | ❌ 危险 |
|------|---------|---------|---------|
| 团队对多租户的理解 | 知道是架构升级，主动讨论决策 | 认为"加个字段就好" | 还没开始想 |
| 当前技术债务 | 有记录，有清理计划 | 有感觉但没量化 | 不清楚 |
| 组织转型节奏 | 有弹性，能同步推进 | 在赶进度，顾不上 | 灭火模式 |

## 实施路线

### M0 认知对齐（1-2 周）

目标：防止团队用单租户思维做多租户改造。

- 架构认知工作坊：为什么这不是加字段，是范式重构
- 最小多租户 POC：用代码验证核心假设（隔离方案、性能基线）
- 架构决策记录机制建立（ADR）
- 外部评审介入，打破团队思维定势

### M1 基础设施（2-3 周）

目标：跑通一个隔离环境。

- 租户路由中间件
- 租户管理服务（创建、配置、启停）
- 隔离策略落地：**从逻辑隔离起步，第三个租户再抽象**
- 数据迁移方案 + 灰度回滚预案

### M2 核心改造（4-6 周）

目标：核心模块多租户化。

- 用户/权限/计费/订单模块按优先级改造
- 存量数据灰度迁移
- 每两周一次"整合"：回顾、文档、更新规范

### M3 迁移治理（2-3 周）

目标：旧系统下线，全量运行。

- 剩余模块迁移
- 旧系统并行运行 → 安全下线
- 租户管理规范、监控、自愈机制建立

### M4 持续演进

目标：规范在实践中自然生长。

- 不预设标准，让治理从运维中沉淀
- 按"第三个同类需求"触发新抽象

## 隔离模式选择

```
逻辑隔离 ──→ Schema 隔离 ──→ 实例隔离
（共享 DB）    （独立 Schema）   （独立 DB）
```

| 模式 | 适用 | 迁移条件 |
|------|------|---------|
| 逻辑隔离 | 早期、低成本、快速上线 | 默认起始模式 |
| Schema 隔离 | 数据安全要求提升 | 第三个租户提出同类安全需求 |
| 实例隔离 | 高安全/独立 SLA | 第三个租户提出同类 SLA 需求 |

**核心原则**：从简起步，按需升级。不要在只有一个租户时设计十个租户的架构。

---

## 节奏管理

| 阶段 | 时长 | 交付物 | 缓冲 |
|------|------|--------|------|
| M0 | 1-2 周 | 共识方案 + POC 结果 | — |
| M1 | 2-3 周 | 隔离环境 + 租户管理 | 3 天 |
| M2 | 4-6 周 | 核心模块上线 | 1 周 |
| M3 | 2-3 周 | 旧系统下线 | 3 天 |
| M4 | 持续 | 治理体系 | — |

**规则**：任何阶段如果连续 3 周无可见产出，重新评估计划——这不代表失败，说明前提假设需要调整。

## 你可能有的疑虑（以及事实）

以下来自同类项目的真实经验：

| 你可能觉得 | 事实是 |
|-----------|--------|
| 加个 tenant_id 就够了 | 需要范式级重构，从数据模型到运维体系 |
| 一步到位最省事 | 渐进迁移更可控，每阶段可回滚 |
| 标准先定好再动手 | 标准化在实践中自然形成 |
| 升级只是技术问题 | 最大瓶颈是团队认知和节奏管理 |
| 隔离模式一步到位最省心 | 从简起步，按"第三个同类需求"触发升级 |
| 招人就能加速 | 体系化设计比堆人力更有效 |
| POC 验证成功等于架构可行 | 技术可行 ≠ 业务合理，需要独立评估 |
