## Step 1：拆解源 schema（已复用 source-schemas.md）

source-schemas.md 是首次提取的产物。验证方法要求检查它是否完整：

| 检查项 | 结果 |
|-------|------|
| 所有 9 个 domain 是否覆盖？ | ✅ |
| 每个 schema 的 entities/causals/boundaries/mappings/角色 是否齐全？ | ✅ |
| 是否包含 biases（反例知识）？ | ❌ source-schemas.md 未包含 biases——这是遗漏 |

**修正**: biases 包含"信念→事实"结构，是最易迁移的反例知识类型。需要在提取中包含 biases。

以 infra 为例，遗漏的 biases：

```
belief: 备份越多越安全
fact: 体系化治理比堆叠备份更有效
```

→ 反例映射：在技术升级中，"功能越多越安全"是错误信念，体系化设计才是正解。

## Step 2：做映射（按类型）

### 2.2 识别映射类型

以 3 个 domain 为例，完整执行映射类型识别：

#### think — 结构同构映射

```
源: 人类反馈 → 辩论收敛 → 章程生成
目标: 外部评审 → 方案收敛 → ADR 记录

映射类型判定:
- entities: 人类反馈 vs 外部评审（都是"来自外部的纠正信号"）
- causals: 反馈→收敛 vs 评审→收敛（因果方向相同）
- 保留: "外部信号打破内部局部最优"这个关系结构
- 丢弃: AI 辩论的具体机制（客户团队并非 AI）
- 类型: ✅ 结构同构
```

#### innov — 隐喻迁移

```
源: POC → 验证 → 复制
目标: 技术选型 PoC → 验证 → 全面推广

映射类型判定:
- entities: POC vs PoC（字面同构，但语境不同——研发 vs 技术架构）
- causals: 验证→复制 vs PoC→推广（方向一致）
- 核心约束: innov 的 POC 周期不超过 2 周 → 技术 PoC 也应设时间 box
- 类型: ✅ 隐喻迁移（需要验证核心约束）
```

#### org — 结构同构 + 反例

```
源 causal: 依赖人治 → 脆弱
目标: 依赖个人运维 → 系统脆弱

源 biases:
  - belief: 招人补位即可
  - fact: 制度化才是根本
→ 反例: 技术升级中"加人就能解决"是错误信念，体系化才是根本

类型: ✅ 结构同构（causal）+ 反例（biases）
```

### 2.3 记录决策过程

以 infra 为例，记录完整推理路径：

```
源 schema: infra
源 causal: 被动防守 → 数据丢失风险 vs 主动设计 → 安全可靠平台

推理路径:
1. 观察到 infra 的 causal 是一个"转型叙事"结构
2. 转型叙事 = [当前状态差 → 原因] vs [目标状态好 → 方案]
3. 询问：技术升级在结构上是什么？
4. 回答：也是转型叙事——[当前单租户有瓶颈, 目标多租户]
5. 保留：转型叙事的方向结构（从 A 到 B 的迁移路径）
6. 丢弃：具体内容（备份策略、工具链 → 替换为租户隔离、路由等）
7. 额外发现：infra 的"三次抽象原则"是一个通用规则，可直接迁移
   → "任何通用抽象在出现第三次之前都是过度设计"

映射类型: 结构同构
保留: 转型叙事的"当前→目标"方向
丢弃: 具体的技术细节
额外: "三次原则"作为通用规则直接迁移
```

## 验证结论

### 可复现性：✅ 方法可用

与第一次（错误）的迁移对比：

| 维度 | 第一次（直觉） | 第二次（按方法） |
|------|-------------|----------------|
| 映射结果 | 一致但不完整 | 一致且完整（含 biases） |
| 推理路径 | 未记录 | 每步有记录 |
| 不可迁移部分 | 凭感觉 | 有约束标记的明确依据 |
| 反例知识 | 未使用 | 9 个 domain 的 biases 均被利用 |
| 可验证性 | 无法验证 | 每步可回溯 |

### 发现的方法缺陷

1. **Step 1 缺少 biases 提取** — source-schemas.md 遗漏了反例知识
2. **Step 2.2 缺少 properties/dynamics 的映射规则** — 当前只定义了 4 种映射类型
3. **约束标记的记录不够精确** — 需要标注"在什么条件下可解除约束"
