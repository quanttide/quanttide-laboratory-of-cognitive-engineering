- 用途: 适用于创始人在组织转型期做决策时参考

  - 实体: 制度

### Situation（1个）

- Agenda: 在核心成员突然离职的冲击下维持团队基本盘稳定，核心目标是建立反脆弱机制防止人才流失导致业务崩塌，次级目标是逐步摆脱对个人管理的过度依赖。
- Frame: 将财务离职理解为一次团队韧性的压力测试（"反脆弱实验"），认为只要能维持住基本盘就证明组织在成熟；但随后发现简单的"招人补位"不足以解决根本问题——制度化虽然必要，却会丧失人治时期的组织温度。
  - org ──[conflict]──▶ meta : 组织管理的制度化需求（法治）与温度保留（人治）之间需保持平衡，而元职能的纯粹标准化倾向若过度推进将加速组织温度流失，偏离org意图寻求的中间态
  - org ──[trigger]──▶ health : 财务离职冲击（组织韧性压力测试）直接触发身心健康危机——高强度应对、不确定性焦虑、工作量激增加剧疲劳和无意义感

### **2. 技术升级方案：适应性多租户架构 (Adaptive Multi-Tenant Architecture)**

本方案旨在解决SaaS模式与聚合平台模式两种需求，同时最小化对当前组织运作的冲击。

**核心设计原则：**
*   **渐进式迁移：** 不一次性重写，通过中间层实现平滑过渡。
*   **元数据驱动：** 利用“元”（meta）的思维，通过配置而非代码区分租户模式。
*   **隔离与共享的灰度：** 允许不同租户有不同的隔离级别（从数据库隔离到Schema隔离），以适配SaaS和聚合平台的不同安全要求。

#### **2.1 架构蓝图：基于“租户域”的分层设计**

我们引入一个名为 **“租户域” (Tenant Domain)** 的抽象层，位于应用与基础设施之间。

**层次结构：**
1.  **接入层（API Gateway / Load Balancer）：** 识别`Tenant-ID`（来自域名、Header或JWT）。
2.  **应用层（Application Services）：** 业务逻辑代码。**关键变化**：代码中不再直接访问数据库，而是通过 **Tenant Context** 对象获取当前租户的配置和数据库连接。
3.  **租户域层 (Tenant Domain Layer)：** 这是一个**新引入的轻量级服务**，负责：
    *   **租户路由：** 维护一个“租户ID -> 资源映射表”（如：租户A -> 数据库集群1, Schema_1；租户B -> 数据库集群1, Schema_2；聚合平台租户C -> 共享Schema）。
    *   **模式区分：** 通过配置标记`tenant_mode: "saas"` 或 `"aggregator"`。`saas`模式倾向于独立的资源池和计费；`aggregator`模式则使用一套共享资源，但通过数据隔离字段（`tenant_id`）来区分。
    *   **配置管理：** 提供API接口，用于动态注册新租户、修改租户配置、调整隔离级别。
4.  **数据层（Data Layer）：**
    *   **混合策略：** 支持三种隔离模式。
        *   **Dedicated Database (DB):** 为VIP客户或聚合平台的大客户提供完全独占数据库。
        *   **Shared Database, Dedicated Schema:** 默认推荐模式。在一个数据库实例中，为每个租户创建单独的Schema，兼顾隔离性和成本。
        *   **Shared Database, Shared Schema:** 最小的“聚合平台”模式。所有数据在一个Schema下，通过`tenant_id`字段逻辑隔离。成本最低，灵活性最低。

#### **2.2 关键升级点与解决方案**

*   **数据迁移：**
    *   **方案：** 开发一个**数据迁移服务**。
    *   **工作流：** 将现有单租户数据作为 `Tenant_0`。对于新租户，自动创建Schema并运行初始化脚本。无需暂停现有服务。
*   **计费与计量 (Billing & Metering)：**
    *   **方案：** 建立一个**计费中心**。
    *   **模式区分：** `saas模式下`，支持按Seat、API调用量、存储量计费。`aggregator模式下`，支持按“平台抽成”或“固定月费”计费。所有计费事件通过消息队列异步发送。
*   **隔离安全：**
    *   **方案：** 在**租户域层**强制执行`Tenant-ID`验证。所有数据库查询、缓存键、队列消息都必须包含`Tenant-ID`。这是防止数据泄露的第一道防线。

#### **2.3 与现有系统元素的结合**

*   **复用“innov”的POC范式：** 将本升级方案本身作为一个大型“POC”。第一阶段只迁移一个新租户，验证“租户域层”的稳定性和性能，收集反馈，再大规模推广。这完全符合创始人“快速试错、小步快跑”的节奏。
*   **利用“infra”的自动化：** 将“租户注册”和“Schema自动创建”的流程集成到已有的CI/CD和自动化备份系统中，实现“一键添加租户”的自动化治理。这能直接解决`infra`领域“理清工具链归属”的痛点。
