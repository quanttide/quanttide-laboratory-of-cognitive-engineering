# 迁移映射表

对每个源 schema，映射到"技术升级"目标问题。

---

## 1. think（收敛机制）

| 源结构 | 技术升级对应 |
|--------|------------|
| 人类反馈打破 AI 局部最优 | 外部专家评审打破团队架构思维定势 |
| 辩论→章程→结构化知识 | 技术方案评审→架构决策记录（ADR）→可复用的升级模式 |
| 意图工程驱动一切生成 | 以"升级意图"为单元驱动所有改造决策 |

**不可迁移**: 创始人- AI 辩论模式需要双方都具备高认知能力，客户团队不一定有同等条件。

## 2. innov（发散引擎）

| 源结构 | 技术升级对应 |
|--------|------------|
| POC 验证→结构化复制 | 先做最小可行多租户 POC → 验证后全面推广 |
| 人机互补循环 | 工具自动化 + 人工决策的协作模式 |
| 低耗能维持产出 | 升级过程中保持"最小干扰"策略，降低业务影响 |
| 整合驱动上升循环 | 每次迭代后回顾总结，驱动下一轮升级 |

**不可迁移**: 创始人的"默认日志做 POC"依赖高度自律的记录习惯，客户团队需要更结构化的流程。

## 3. org（抗脆弱机制）

| 源结构 | 技术升级对应 |
|--------|------------|
| 依赖人治→组织脆弱 | 依赖个人运维→系统脆弱 |
| 制度化→韧性增强 | 建立标准化 DevOps 体系→系统韧性增强 |
| 法治与人治同步推进 | 自动化与人工干预并存，逐步过渡 |
| 反脆弱机制 | 升级过程中的回滚/容错/灰度机制 |
| 温度保留 | 升级过程中保持开发者体验和团队士气 |

**不可迁移**: 5-50人小微组织的管理方式与客户的技术团队规模不直接对应。

## 4. infra（平台底座）

| 源结构 | 技术升级对应 |
|--------|------------|
| 被动防守→主动设计 | 从救火式运维转向体系化治理 |
| 工具链归属不清→架构熵增 | 升级中明确架构边界和团队职责分工 |
| 至少三个实例才进入抽象层 | "三次重复"原则——出现第三次才做通用抽象 |
| 过度抽象本身也是风险 | 避免过度设计多租户隔离机制 |

**最容易直接迁移** — 技术架构问题场景最接近。

## 5. meta（治理层）

| 源结构 | 技术升级对应 |
|--------|------------|
| 元智能成熟→系统自我维护 | 升级后平台的自运维/自愈能力 |
| 标准化是自然产出 | 规范从实践中生长，非预先设计 |
| 归并冗余规则集 | 升级中清理历史包袱，合并重复配置/代码 |

**不可迁移**: "需要系统运行至少三个月"的前提——客户系统可能还不满足这个条件。

## 6. health（元意图）

| 源结构 | 技术升级对应 |
|--------|------------|
| 元意图保障可持续 | 升级节奏需要可持续，避免"大爆炸"重写 |
| 无意义感对冲→整合 | 快速展示进展（里程碑）以维持团队动力 |

**最特殊** — 创始人是个人，客户是团队。health 更多映射到**项目管理节奏**而非技术。

## 7. business（商业 POC）

| 源结构 | 技术升级对应 |
|--------|------------|
| 低门槛验证→可行后复制 | 技术选型先做 PoC 验证可行再全面采用 |
| 验证失败→低成本放弃 | 技术路线要有容错和回退策略 |
| 验证成功≠商业价值 | 技术可行 ≠ 业务合理 |

**关键映射**: 商务的"先验证后投入"模式直接对应技术升级中的"先 PoC 后推广"策略。

## 8. product（范式迁移）

| 源结构 | 技术升级对应 |
|--------|------------|
| 不是 UI 技巧，是范式问题 | 多租户不是功能添加，是架构范式升级 |
| 阅读器而非编辑器视角 | "多租户优先"思维而非"单租户改改" |
| 范式尚未收敛→高风险 | 多租户模式选型未收敛前保持灵活 |

**最关键的认知迁移**: 客户可能以为多租户是"加个 tenant_id 字段"，实际上是架构范式重构。

## 9. write（迭代引擎）

| 源结构 | 技术升级对应 |
|--------|------------|
| 原型→框架迭代 | 技术方案从 MVP 到成熟架构的渐进演进 |
| 碎片→整合→上升循环 | 升级中积累经验 → 整合成规范 → 驱动下一轮 |

**核心模式**: 技术升级不是一次性工程，而是持续迭代过程。

---

## 不可迁移的部分汇总

| 源 domain | 不可迁移的原因 |
|-----------|--------------|
| think | 创始人-AI 辩论模式依赖双方高认知能力 |
| innov | 高度自律的个人记录习惯难复制到团队 |
| org | 小微组织管理方式 vs 客户技术团队规模不同 |
| meta | "运行三个月"的条件客户可能不满足 |
| health | 个人身心调节 vs 团队节奏管理，主体不同 |

**核心差异**: 创始人是"一个人+AI"的工作模式，客户是"团队"的工作模式。迁移时需要从**个人认知**映射到**组织流程**。
