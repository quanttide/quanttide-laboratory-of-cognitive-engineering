# Schema 质量评估框架

双来源合并：图式理论（Source A）+ 工程实践（Source B）。评分统一为 1-5 分。

## Source A：从图式理论推导

### A-1 覆盖度（Coverage）

图式的默认值填充机制——当信息缺失时，图式能否提供合理的默认行为。

| 分数 | 标准 |
|------|------|
| 5 | 所有关键场景都有显式默认值，缺失时行为可预测 |
| 4 | 主要场景有默认值，边缘场景有说明 |
| 3 | 部分场景有默认值，但有明显缺口 |
| 2 | 少量默认值，大部分行为需外部补充 |
| 1 | 无默认值，图式只描述了结构 |

**检查点**：properties 中的 key 是否覆盖了 entities 中所有可能需要默认值的属性？dynamics 是否描述了典型演化路径？

### A-2 灵活性与可修正性（Flexibility）

图式的同化/顺应机制——能否区分"跨组织通用"和"依赖条件"的知识。

| 分数 | 标准 |
|------|------|
| 5 | 显式区分保留类/需验证类，每类有明确的判定和验证规则 |
| 4 | 有区分，但部分边界模糊 |
| 3 | 隐含区分但未显式标记 |
| 2 | 无区分，所有因果链同等对待 |
| 1 | 因果链未经结构化拆解，混合在一起 |

**检查点**：causals 中是否有 type 标记？需验证类是否有 verify 字段？

### A-3 复杂度与认知负荷（Complexity）

图式的层次组织——实体和关系的层级是否合理。

| 分数 | 标准 |
|------|------|
| 5 | 有清晰的层级结构，主图式含子图式，认知负荷合理 |
| 4 | 扁平结构但 entity 数量适中（3-7 个），causal 数量可控（5-12 条） |
| 3 | 扁平但 entity 或 causal 过多，难以一次性理解 |
| 2 | 结构混乱，无明确组织原则 |
| 1 | 不可理解的复杂或无结构 |

## Source B：从工程实践引入

### B-1 内部一致性（Internal Consistency）

schema 内部无矛盾——causals、mappings、biases 之间逻辑自洽。

| 分数 | 标准 |
|------|------|
| 5 | 所有字段之间完全自洽，无冲突 |
| 4 | 少量可解释的不一致（如偏见和因果链互补而非冲突） |
| 3 | 存在一致性问题但可调和 |
| 2 | 多个明显矛盾 |
| 1 | 字段之间相互矛盾，无法使用 |

**检查点**：causals 和 biases 是否矛盾？（如 causal 说"POC 验证可降低风险"，但 bias 说"客户不需要 POC"）

### B-2 外部有效性（External Validity）

schema 与真实数据的对应关系——每个字段能否追溯到原始 journal 数据。

| 分数 | 标准 |
|------|------|
| 5 | 每条 causal、mapping、bias 都有 journal 数据来源引用 |
| 4 | 大部分有来源，少量基于经验补充并有标注 |
| 3 | 部分有来源，部分来源不明 |
| 2 | 少量有来源，大部分无追溯 |
| 1 | 全部为经验判断，无可追溯来源 |

### B-3 任务适用性（Task Fit）

schema 是否适用于其声明的场景。

| 分数 | 标准 |
|------|------|
| 5 | usage 和实际场景精确匹配，mappings 可直接执行 |
| 4 | 匹配度高，但需要少量调整 |
| 3 | 中等匹配，部分 mappings 需要改造 |
| 2 | 低匹配，仅少数部分可用 |
| 1 | 完全不匹配，usage 与实际需求无关 |

### B-4 可沟通性（Communicability）

新人是否能理解并使用这个 schema。

| 分数 | 标准 |
|------|------|
| 5 | 术语一致、结构清晰、新人通读后即可使用 |
| 4 | 需要少量上下文解释 |
| 3 | 需要阅读配套文档才能理解 |
| 2 | 术语不一致或不清晰，理解困难 |
| 1 | 无法自解释，必须由作者亲自讲解 |

## 总分计算

总分 = 7 维度分数之和 / 7

| 等级 | 范围 | 含义 |
|------|------|-----|
| 优秀 | 4.0-5.0 | schema 可直接用于生产 |
| 良好 | 3.0-3.9 | schema 可用，需针对性改进 |
| 待改进 | 2.0-2.9 | schema 有结构性缺陷 |
| 不合格 | 1.0-1.9 | schema 不可用，需重构 |

## 用法

1. 评估 schema 时，为每个维度打分
2. 注明关键扣分点和依据
3. 总分作为基线记录在 `data/baseline-assessment.md`
4. 每次修改后重新评估，追踪质量变化
